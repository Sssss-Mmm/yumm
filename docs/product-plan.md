## 1. 배경과 문제 정의

혼자 밥 먹는 것 자체가 문제는 아니다. 문제는 **"같이 먹고 싶은데 같이 먹을 사람을 그때 구할 수 없다"**는 것이다.

기존 수단이 해결하지 못하는 지점:

| 수단 | 한계 |
|---|---|
| 지인에게 연락 | 시간·지역이 안 맞으면 끝. 매번 부탁하는 부담 |
| 오픈채팅방 | 누가 나올지 모름, 인원 조율이 수동, 대화가 흘러가면 묻힘 |
| 소개팅/데이팅 앱 | 목적 자체가 다름. 사람을 사귀러 가는 곳이지 끼니를 해결하러 가는 곳이 아니다 |

**yumm의 답**: 조건이 맞는 **3~4인**을 시스템이 자동으로 묶는다.
3~4인인 이유는 **그게 밥자리의 자연스러운 크기**여서다. 대화가 한 사람에게 몰리지 않고,
한 명이 못 나와도 밥은 먹는다. 이 인원 제약이 서비스 설계 전체를 결정한다.

> **포지셔닝 원칙**: yumm의 경쟁 상대는 데이팅 앱이 아니라 **오늘 혼자 먹게 될 그 한 끼**다.
> 사용자가 앱을 여는 이유는 "누굴 만나고 싶어서"가 아니라 **"오늘은 혼자 먹기 싫어서"**다.
> 기획·카피·화면 어디서든 이 동기를 기준으로 판단한다. 데이팅 앱과 비교해 우리를 설명하는 순간
> 그쪽이 기준점이 되고, 그 기대로 들어온 사용자가 실제 사고와 신고를 만든다.

**다만 2인은 예외적으로 허용한다.** 사용자가 직접 "2명이어도 괜찮다"를 선택했고, 상대도 똑같이 선택했으며,
3인을 끝내 못 모은 경우에 한한다. 3~4인이 기본이고 2인은 폴백이다. 자세한 근거는 5번(유동성)에 있다.

> **용어 원칙**: 이 서비스에 "1:1 매칭"은 없다. 문서·UI·마케팅 어디에서도 "1:1"이라는 표현을 쓰지 않고
> "2인"으로만 부른다. 부정형("1:1이 아닙니다")도 쓰지 않는다 — 언급하는 순간 그게 기준점이 된다.

## 2. 목표와 성공 지표

### 북극성 지표
**주간 실제 성사된 식사 수** (매칭 수가 아니라 **실제로 만난** 수)

### 단계별 지표

| 구분 | 지표 | MVP 목표 |
|---|---|---|
| 획득 | 주간 신규 가입 | — |
| 활성 | 신청 → 매칭 성사율 | 60% 이상 |
| 활성 | 평균 대기 시간 | 15분 이내 |
| **핵심** | 매칭 → 실제 만남 전환율 | 70% 이상 |
| **핵심** | 노쇼율 | 15% 이하 |
| 유지 | 4주 내 재신청률 | 40% 이상 |
| 안전 | 신고 건수 / 만남 100건 | 1건 이하 |
| 폴백 | 2인 그룹 비중 | 30% 이하 (넘으면 유동성이 부족하다는 신호) |
| 폴백 | 2인 그룹의 노쇼율 vs 3~4인 노쇼율 | 격차 2배 이내 |

> 지금 코드에는 이 중 **어느 것도 측정되지 않는다.** 매칭 성사율과 노쇼율을 못 보면 버킷 설계가 맞는지, 3인 마감이 맞는지 판단할 근거가 전혀 없다. 지표 수집을 MVP 범위에 포함해야 한다.

## 3. 타깃 사용자

### 1차 타깃
수도권 주요 업무·대학 상권에서 **점심/저녁을 혼자 해결하는 20~30대**.

**페르소나 A — 신입사원 (27세, 판교)**
팀 점심에 매번 끼기도 애매하고, 그렇다고 매일 편의점에서 혼자 때우기도 지친다.
오늘 점심 한 끼만 같이 먹을 사람이면 충분하다. → **가벼움**이 핵심 가치.

**페르소나 B — 자취 대학원생 (25세, 신촌)**
저녁을 계속 혼자 먹다 보니 끼니 자체를 대충 넘기게 된다. 거창한 모임이 아니라
제대로 된 밥 한 끼를 누군가와 먹고 싶다. → **오늘 당장 성사되는 것**이 핵심 가치.

두 사람 모두 **사람을 사귀러 오는 게 아니라 밥을 먹으러 온다.** 이 구분이 기능 판단의 기준선이다.

### 명시적 비타깃
연인/소개팅 목적, 홍보·영업 목적, 대규모 모임 주최자.
(→ 이 경계를 지키는 장치가 **신고·차단·이용약관**이며, 현재 전부 없다)

## 5. 최대 리스크: 유동성 (Liquidity)

**이 서비스가 실패한다면 알고리즘 때문이 아니라 사람이 안 모여서다.**

매칭이 성사되려면 **같은 지역 + 같은 날짜 + 같은 시간대**에 3명 이상이 30분 안에 겹쳐야 한다. 버킷을 잘게 쪼갤수록 매칭 품질은 오르지만 성사 확률은 급락한다. 제한을 두지 않으면 `지역 × 날짜 × 시간대` = 7 × 7일 × 2 = **98개 버킷**이 된다. 초기 사용자가 100명이어도 버킷당 평균 1명이다. **아무도 매칭되지 않는다.**

아래 전략을 적용하면 이렇게 줄어든다.

| 조건 | 버킷 수 |
|---|---|
| 제한 없음 (지역 7 × 7일 × 2) | 98 |
| 날짜를 당일+익일로 제한 (7 × 2 × 2) | 28 |
| **+ 오픈 지역 1곳 (1 × 2 × 2)** | **4** ← MVP 목표 |

이 문제는 설계 노트에 없다. MVP 운영 전략으로 대응한다:

| 전략 | 내용 |
|---|---|
| **지역 축소** | 오픈은 1~2개 상권만 (판교 또는 강남). 7개 동시 오픈은 유동성을 7등분하는 자살행위 |
| **날짜 축소** | 당일 + 익일만 허용. 일주일 뒤 신청은 대기열만 희석시킨다 |
| **시간 집중** | 특정 요일·시간대에 신청을 몰아주는 "밥약 타임" 운영 (예: 평일 점심 11:00~11:30 신청 창구) |
| **대기 가시화** | "지금 강남 점심에 2명 대기 중" 노출. 대기자가 보이면 신청이 신청을 부른다 |
| **초기 시드** | 오픈 커뮤니티/사내 채널을 통한 동시 유입. 소수를 오래 모으는 것보다 다수를 짧게 모으는 게 낫다 |
| **2인 폴백** | 최소 인원 3 → 2. 아래 참조 |
| **가입 문턱 뒤로** | 가입은 최소 항목만. 인증·동의는 첫 신청 직전으로 미룬다. 아래 참조 |

### 2인 폴백이 유동성 레버인 이유

한 버킷에 3명이 30분 안에 겹칠 확률과 2명이 겹칠 확률은 체감 차이가 아니라 자릿수 차이다.
버킷당 기대 대기자가 1~2명인 초기 단계에서 **최소 인원을 낮추는 것이 매칭률을 올리는 가장 값싼 수단**이다.
구현도 편성 로직의 최소 인원 상수를 후보별 값으로 바꾸는 정도다.

하지만 그대로 켜면 서비스가 바뀐다. 그래서 네 가지 안전장치를 함께 건다.

| 장치 | 내용 |
|---|---|
| **옵트인** | 기본값은 3~4인. "2명이어도 괜찮아요"를 직접 선택한 사람만 대상 |
| **쌍방 조건** | 양쪽 모두 선택했을 때만 성립. 성별 조건과 동일한 하드·관계형 조건이라 `compatible()` 구조를 그대로 재사용한다 |
| **폴백 순서** | 3~4인 편성을 먼저 시도하고, 남은 사람 중 만료 잔여 5분 이내인 경우에만 2인으로 마감 |
| **선행 조건** | 신고·차단·리마인드 알림이 붙은 뒤에 켜는 스위치. 2인은 노쇼에 가장 취약하고 안전 리스크가 가장 크다 |

**2인의 구조적 약점**: 3인은 한 명이 안 나와도 밥은 먹는다. 2인은 한 명이 안 나오면 **0명**이다.
노쇼 취약성이 두 배가 아니라 질적으로 다르다. 확정 절차를 두지 않기로 한 결정(6번)과 정면으로 부딪히는
지점이라, 식사 당일 리마인드를 2인 폴백의 **필수 선행 요건**으로 못박는다.

### 가입 문턱은 없애지 않고 뒤로 미룬다

현재 가입에 필요한 항목이 6개(이메일·비밀번호·닉네임·성별·나이·전화번호)다.
그중 **전화번호는 저장·수정만 되고 어디에도 쓰이지 않는다.** 문자 발송도, 화면 노출도, 매칭 사용도 없다.
"밥 같이 먹을 사람 찾기"에 전화번호를 요구하면 그 자리에서 이탈한다.

| 시점 | 요구하는 것 |
|---|---|
| 가입 | 이메일 · 비밀번호 · 닉네임 · 성별 · 생년 — 끝 |
| 둘러보기 | 없음. 지역별 대기 인원까지 비로그인으로 보여준다 |
| **첫 신청 직전** | 이메일 인증 + 약관 동의 + 안전 수칙 — **한 화면에서 한 번** |

게이트 개수는 그대로인데 체감 문턱은 절반 이하가 된다. 가입 시점엔 잃을 게 없으니 들어오고,
실제로 신청할 마음이 생긴 뒤에 인증을 요구하므로 이탈률이 낮다.

**다만 순서를 착각하면 안 된다. 가입자를 늘리는 것보다 첫 신청을 매칭시키는 게 중요하다.**
1,000명을 모아도 버킷당 3명이 안 겹치면 전원 이탈한다. 반대로 가입이 다소 번거로워도
첫 신청에서 매칭되면 남는다. 유입이 걱정될 때 손대야 할 곳은 **문턱보다 지역 집중**이다.

## 6. 사용자 여정 — 현재 설계의 끊긴 지점

```
[가입] → [로그인] → [조건 입력] → [대기] → [매칭 성사] → ??? → [식사]
                                                        ↑
                                             여기서 여정이 끊긴다
```

**현재 매칭 성사 이후에 존재하는 것**: 그룹원 닉네임 목록, 그룹 채팅방(대화 저장 안 됨, 웹 화면 없음).

**존재하지 않는 것**:
- 웹 채팅 화면 → 방은 열리는데 들어갈 UI가 없다. 콘솔 클라이언트만 존재한다
- 대화 기록 → 저장하지 않아 새로고침하면 사라진다. 약속을 잡는 채팅인데 기록이 없다
- 이탈 경로 → 매칭 후에는 취소 API가 동작하지 않아 빠져나갈 방법이 없다
- 그룹 해체 처리 → 인원이 최소치 밑으로 떨어져도 깨진 그룹으로 방치된다

### 확정 절차는 만들지 않는다

"매칭 후 N분 내 전원 확정" 단계를 검토했지만 넣지 않기로 했다. **확정하라는 사실을 사용자가 알 방법이
없기 때문이다.** 푸시도 웹소켓 알림도 없는 상태에서 기한을 걸면 확정을 안 한 사람과 확정할 기회가
없었던 사람이 구분되지 않아, 잘못 없는 사람이 노쇼 처리된다.

**대신 채팅으로 흡수한다.** 실제 사람은 확정 버튼을 누르는 게 아니라 채팅방에서 "저 갈게요,
몇 시에 볼까요?" 하고 약속을 잡는다. **채팅방 입장이 곧 참석 의사다.** 몇 시에 어디서 만날지도
시스템이 정하지 않고 그룹이 정한다 — `MealTime`이 `LUNCH`/`DINNER`뿐이라 역산할 시각 자체가 없다.

이 결정은 알림 인프라가 생기면 재검토한다. 재검토 시 원칙은 두 가지다.
3인 확정 + 1인 미확정이면 3인으로 진행하고, 시스템 탓의 미확정은 노쇼로 기록하지 않는다.

**단, 이 결정 때문에 2인 폴백의 리마인드 알림이 선택이 아니라 필수가 된다.** (5번 참조)

### 개선 여정 (to-be)

```
조건 입력(2인 허용 여부 포함) → 대기(잔여시간·대기인원 노출)
  → 3~4인 편성 / 만료 임박 시 2인 폴백
  → 매칭 성사 알림(이메일/푸시)
  → 채팅방 입장 = 참석 의사 → 시각·장소 합의 → 약속 카드 고정
  → 이탈 시 남은 구성원에게 알림, 최소 인원 미달이면 해체 후 대기열 복귀
  → 식사 당일 아침 리마인드
  → 식사
  → 참석 상호 체크 → 노쇼 기록 / 신고·차단
```

## 7. MVP 범위

### MVP에 반드시 포함 (P0)

| 영역 | 항목 | 사유 |
|---|---|---|
| 매칭 | 주기적 편성 스케줄러 | 현재는 신규 신청이 없으면 3명이 대기해도 안 묶인다 |
| 매칭 | 지역 `Region` enum화 + 서버 날짜 검증(당일~익일) | 버킷 키가 자유 문자열이면 매칭이 조용히 실패한다. 날짜 범위는 유동성 전략(5번)의 실행 지점 |
| 매칭 | **2인 폴백** (옵트인 + 쌍방 + 만료 임박 시에만) | 유동성 문제의 가장 값싼 해법 |
| **이탈** | 매칭 후 이탈, 최소 인원 미달 시 그룹 해체 + 대기열 복귀 | 지금은 매칭되면 빠져나갈 방법이 없다 |
| 채팅 | 메시지 저장 + 조회 + **웹 채팅 화면** | 현재 콘솔 클라이언트만 존재 |
| 알림 | 매칭 성사·그룹 해체 알림 (최소 이메일) | 30분 대기 결과를 폴링으로만 아는 건 결함 |
| 알림 | **식사 당일 아침 리마인드** | 확정 절차를 두지 않기로 한 만큼 유일한 노쇼 억제 수단. 2인 폴백의 선행 요건. "1시간 전"이 아닌 이유는 시스템에 만날 시각이 없어서다(8절) — `requirements.md` FR-N-04 참조 |
| **안전** | 신고, 차단, 안전 수칙 고지, 약관 동의 | 낯선 사람 대면 서비스의 출시 최소 조건 |
| 계정 | 가입 항목 축소(전화번호 제거, `age`→생년), 이메일 인증·약관·안전수칙을 **첫 신청 직전 한 화면**으로 통합 | 안전 게이트는 유지하되 유입을 막지 않는 위치로 옮긴다 |
| 계정 | 만 19세 이상 제한 (생년 입력 확인, 별도 본인인증 없음) | 성인 1명 + 미성년자 1명의 2인 조합을 시스템이 만들지 않게 한다 |
| 운영 | 매칭 지표 — **스케줄러 실행당 로그 한 줄이 전부**(버킷 수/대기자/편성 그룹 수). 지표 테이블·API는 M6 | 사용자 0인 시점에 대시보드는 과하다 |

### v1.1 (출시 직후)

나이대 조건, 노쇼 이력·페널티, 재신청(조건 재사용), 대기 인원 노출, 약속 카드(시각·장소 고정), 참석 상호 체크, 관리자 신고 처리 화면, refreshToken 자동 갱신.

### 이후

한 줄 소개·관심사 프로필, 만남 후 상호 평가, 식당 추천, 자유 텍스트 취향 + 임베딩(H2 실패 시), 지역 확장, **알림 인프라 확보 후 확정 단계 재검토**.

### 범위 밖
결제·더치페이, 정기 모임, 네이티브 앱, 위치 실시간 공유.
**"1:1 매칭"이라는 기능·표현은 제공하지 않는다** (1번 용어 원칙 참조).

## 8. 유지할 기획 결정 (설계 노트 승계)

이 결정들은 근거가 타당하므로 그대로 간다. 상세 논거는 `docs/matching-design.md` 참조.

| 결정 | 근거 요약 |
|---|---|
| 조건은 카테고리 선택, 자유 텍스트·임베딩 안 씀 | 매칭 근거를 설명할 수 있고, 콜드 스타트가 없으며, 인프라가 Spring 하나로 끝난다 |
| 조건을 하드(버킷) / 하드-관계형(쌍방검사) / 소프트(점수)로 분리 | 성별 조건은 상대에 따라 결과가 달라져 버킷 키가 될 수 없다 |
| 그리디 편성 (선착순 씨앗 + 취향 최대 겹침) | 대기 서비스에서는 최적성보다 "먼저 온 사람이 먼저"라는 공정성이 중요 |
| 대기열은 DB 테이블, Redis 안 씀 | 버킷 전체를 읽어 분할하는 건 쿼리의 일 |
| 만료는 저장 상태가 아니라 시각 비교로 계산 | 만료 배치가 필요 없어진다 |
| 동시성은 비관적 락 | `synchronized`는 트랜잭션 커밋 전에 풀려 실제로 막지 못한다 |
| 채팅방 ID = groupId | 방을 따로 만들 필요가 없고 구성원 = 참여자가 자동 성립 |
| 확정 단계를 두지 않고 채팅 입장으로 대신함 | 알림이 없으면 "확정 안 한 사람"과 "확정할 기회가 없던 사람"이 구분되지 않는다 |
| 만날 시각·장소는 시스템이 아니라 그룹이 정함 | `LUNCH`/`DINNER`에서 역산할 시각이 없다. "점심 = 12시"는 지어낸 값이다 |
| 지역을 `Region` enum으로 고정 | **결정 변경(2026-08-28).** 원래는 "지역 단위가 안 정해졌으니 뭘 만들어도 추측"이라 보류했으나, 요구사항 8절이 상권 7곳으로 단위를 확정하면서 전제가 해소됐다. `MealTime`·`FoodCategory`·`GenderPreference`가 이미 전부 enum이라 지역만 자유 문자열인 게 오히려 예외다 |

**`MatchRequest.groupId` 컬럼만으로 그룹을 표현하는 결정은 당분간 유지한다.**
확정 상태·만날 시각·장소를 시스템이 갖지 않기로 했으므로, 설계 노트가 정한 승격 조건("그룹 자체에 속성이 생길 때")이
아직 충족되지 않는다. 약속 카드(v1.1)를 만드는 시점이 승격 시점이다.

## 9. 결정이 필요한 사항

| # | 질문 | 선택지 | 권고 |
|---|---|---|---|
| Q1 | 2인 폴백을 언제 켜나 | MVP 오픈과 동시 / 안전 기능 이후 / 유동성 부족이 관측된 뒤 | **안전 기능 이후.** 구현과 활성화를 모두 M4로 묶는다(2026-08-28 변경). 기능 플래그도 두지 않는다 — 켤 수 없는 코드를 두 마일스톤 동안 들고 갈 이유가 없다. **리마인드(FR-N-04) 미확보 상태에서 M4를 막지는 않는다(2026-08-29).** 그 게이트가 막는 건 실사용자의 노쇼인데 사용자가 0명이고, M3이 외부 의존(이메일 API 키)으로 막혀 있어 기다리면 P0 매칭 로직이 기약 없이 미구현으로 남는다. 게이트는 M5 진입 시점으로 옮긴다. 플래그를 안 두는 결정은 그대로 — FR-M-12 옵트인이 이미 스위치다 |
| Q1-1 | 2인 그룹이 3인으로 늘어날 수 있게 하나 | 성사 후 고정 / 4인까지 추가 합류 허용 | **고정.** 이미 대화가 시작된 방에 사람을 밀어 넣으면 경험이 나쁘다 |
| Q2 | 만날 시각을 누가 정하나 | 신청 시 사용자가 입력 / 그룹장이 제안 / 채팅 합의 | **신청 시 30분 슬롯 선택**(12:00/12:30/18:30…). 버킷 키에 넣으면 조율 비용이 0이 된다. 단 버킷이 더 쪼개지므로 유동성과 트레이드오프 |
| Q3 | 장소 결정 | 사용자 자율 / 서비스가 후보 제시 | MVP는 자율. 다만 "집합 장소"만이라도 구조화해서 저장 |
| Q4 | 노쇼 판정 근거 | 상호 체크 / 신고만 / 위치 인증 | **상호 체크.** 위치 인증은 과하다 |
| Q5 | 오픈 지역 | 7곳 전체 / 1~2곳 | **1~2곳.** 5번(유동성) 참조 |
| Q6 | 프로필 공개 범위 | 닉네임만 / +나이대 / +한줄소개 | **닉네임 + 프로필이미지. 나이대는 공개하지 않는다(변경 2026-08-29).** 원래 권고는 "닉네임 + 나이대"였으나 확정본인 `requirements.md` FR-P-05를 따른다. 매칭 성사 후에는 상대를 고를 수 없어 나이대가 행동을 바꾸지 않고, 카드 구성이 데이팅 앱에 가까워져 1절 포지셔닝 원칙과 마찰한다. 나이대 조건(FR-M-11, M6) 도입 시 공개 여부를 함께 재검토하며, 넣는다면 **20대/30대 10년 단위**다 — `birth_year`만 저장하고 만 19세 판정도 생일 미경과 가정이라 경계가 최대 1년 어긋나, 초·중·후반 표기는 틀린 정보가 된다 |
| Q7 | `yumm-inference` | 유지 / 삭제 | **삭제.** 호출하는 코드가 없고 카테고리 매칭 결정과 상충. H2 실패 시 다시 만든다 |
| Q8 | 연령 하한 | 만 19세 차단 / 만 14세 이상 + 법정대리인 동의 + 연령 분리 / 대학생 인증으로 확장 | **만 19세 차단.** 얻는 유입이 사실상 0인데 연령 분리로 버킷이 갈리면 유동성이 반토막 난다. 근거는 `requirements.md` 3.1 박스 |
| Q9 | 전화번호 | 가입 시 필수 / 선택 / 받지 않음 | **받지 않음.** 현재 어디에도 쓰이지 않으면서 이탈만 만든다. 알림 수단으로 실제 필요해지면 그때 받는다 |

## 11. 마일스톤

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| M0 (완료) | 인증/회원, 매칭 편성 로직, 그룹 채팅 서버, 매칭 웹 화면 | 현재 상태 |
| M1 (완료) | 편성 스케줄러, 지역 enum, 서버 날짜 검증, 지표 로그 | 신규 신청 없이 18초 만에 편성 확인 |
| M2 | **매칭 후 이탈 + 그룹 해체 처리** (2인 폴백은 M4로 이동) | 매칭된 사용자가 빠져나갈 수 있고, 깨진 그룹이 방치되지 않는다 |
| M3 | ~~채팅 저장·조회~~ ~~웹 채팅 화면~~(M1에서 선행 완료) + 매칭/해체 알림 + 식사 당일 리마인드 + `@Scheduled` 전용 스케줄러 분리 | 앱을 켜두지 않아도 매칭을 알 수 있다. **이메일 API 키 확보가 선행 조건** |
| M4 | 신고·차단·약관·안전 수칙·성인 인증 + 이탈자 STOMP 구독 강제 해제(FR-T-02 한계) + **2인 폴백(구현과 활성화를 같이)** | **출시 가능 상태.** 폴백 코드를 M2가 아니라 여기서 쓰는 이유: 스위치를 켤 수 있는 시점이 어차피 여기고, 차단 관계(FR-S-02) 때문에 `compatible()`을 어차피 다시 연다. M2에 넣으면 마일스톤 두 개 동안 죽은 코드로 남고 같은 파일을 두 번 고치게 된다 |
| M5 | 1개 지역 클로즈드 베타 | 매칭→만남 전환율 측정. **진입 전 확인: FR-N-04(리마인드)가 없으면 2인 옵트인 UI를 숨긴 채 시작한다**(FR-G-11) |
| M6 | 노쇼 페널티, 나이대 조건, 약속 카드, 관리자 화면, 지역 확장 | 2인/3~4인 노쇼율 격차 확인 후 폴백 유지 여부 결정 |

**M4 이전에는 외부 공개 출시하지 않는다.**
