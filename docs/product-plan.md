## 1. 배경과 문제 정의

혼자 밥 먹는 것 자체가 문제는 아니다. 문제는 **"같이 먹고 싶은데 같이 먹을 사람을 그때 구할 수 없다"**는 것이다.

기존 수단이 해결하지 못하는 지점:

| 수단 | 한계 |
|---|---|
| 지인에게 연락 | 시간·지역이 안 맞으면 끝. 매번 부탁하는 부담 |
| 오픈채팅방 | 누가 나올지 모름, 인원 조율이 수동, 대화가 흘러가면 묻힘 |
| 소개팅/데이팅 앱 | 목적이 다름. 1:1이라 부담이 크고 "밥 한 끼"에 과한 맥락 |

**yumm의 답**: 조건이 맞는 **3~4인**을 시스템이 자동으로 묶는다.
1:1이 아닌 이유는 명확하다 — 한 사람이 안 나오면 끝나는 구조를 피하고, 처음 만나는 부담을 낮추기 위해서다. 이 3~4인 제약이 서비스 설계 전체를 결정한다.

## 2. 목표와 성공 지표

### 북극성 지표
**주간 실제 성사된 식사 수** (매칭 수가 아니라 **실제로 만난** 수)

### 단계별 지표

| 구분 | 지표 | MVP 목표 |
|---|---|---|
| 획득 | 주간 신규 가입 | — |
| 활성 | 신청 → 매칭 성사율 | 60% 이상 |
| 활성 | 평균 대기 시간 | 15분 이내 |
| **핵심** | 매칭 → 실제 만남 전환율 | 70% 이상 |
| **핵심** | 노쇼율 | 15% 이하 |
| 유지 | 4주 내 재신청률 | 40% 이상 |
| 안전 | 신고 건수 / 만남 100건 | 1건 이하 |

> 지금 코드에는 이 중 **어느 것도 측정되지 않는다.** 매칭 성사율과 노쇼율을 못 보면 버킷 설계가 맞는지, 3인 마감이 맞는지 판단할 근거가 전혀 없다. 지표 수집을 MVP 범위에 포함해야 한다.

## 3. 타깃 사용자

### 1차 타깃
수도권 주요 업무·대학 상권에서 **점심/저녁을 혼자 해결하는 20~30대**.

**페르소나 A — 신입사원 (27세, 판교)**
점심에 팀원들과 매번 같이 먹기가 부담스럽고, 그렇다고 매일 혼자 먹기도 지친다. 오늘 점심만 같이 먹을 사람이면 충분하다. → **가벼움**이 핵심 가치.

**페르소나 B — 자취 대학원생 (25세, 신촌)**
저녁을 계속 혼자 먹는다. 새로운 사람을 만나는 것 자체에 관심이 있지만 1:1은 부담이다. → **3~4인**이 핵심 가치.

### 명시적 비타깃
연인/소개팅 목적, 홍보·영업 목적, 대규모 모임 주최자.
(→ 이 경계를 지키는 장치가 **신고·차단·이용약관**이며, 현재 전부 없다)

## 4. 핵심 가설과 검증

| # | 가설 | 검증 방법 | 실패 시 |
|---|---|---|---|
| H1 | 조건 기반 자동 매칭이면 사람들이 낯선 이와 밥을 먹는다 | 매칭→만남 전환율 70% | 지인 초대 기반으로 선회 |
| H2 | 카테고리 조건만으로 만족스러운 매칭이 된다 | 만남 후 만족도, 재신청률 | 자유 텍스트 취향 + 임베딩 도입 (`yumm-inference` 부활) |
| H3 | 3~4인이 1:1보다 심리적 진입장벽이 낮다 | 신청 전환율, 정성 인터뷰 | 인원 조절 옵션 제공 |
| **H4** | **한 지역·시간대에 3명 이상이 동시에 모인다** | 버킷별 대기 인원 분포 | **버킷 완화 필요 — 아래 5번 참조** |

## 5. 최대 리스크: 유동성 (Liquidity)

**이 서비스가 실패한다면 알고리즘 때문이 아니라 사람이 안 모여서다.**

매칭이 성사되려면 **같은 지역 + 같은 날짜 + 같은 시간대**에 3명 이상이 30분 안에 겹쳐야 한다. 버킷을 잘게 쪼갤수록 매칭 품질은 오르지만 성사 확률은 급락한다. 현재 설계는 `지역 × 날짜 × 시간대` = 7 × 7일 × 2 = **98개 버킷**이다. 초기 사용자가 100명이어도 버킷당 평균 1명이다. **아무도 매칭되지 않는다.**

이 문제는 설계 노트에 없다. MVP 운영 전략으로 대응한다:

| 전략 | 내용 |
|---|---|
| **지역 축소** | 오픈은 1~2개 상권만 (판교 또는 강남). 7개 동시 오픈은 유동성을 7등분하는 자살행위 |
| **날짜 축소** | 당일 + 익일만 허용. 일주일 뒤 신청은 대기열만 희석시킨다 |
| **시간 집중** | 특정 요일·시간대에 신청을 몰아주는 "밥약 타임" 운영 (예: 평일 점심 11:00~11:30 신청 창구) |
| **대기 가시화** | "지금 강남 점심에 2명 대기 중" 노출. 대기자가 보이면 신청이 신청을 부른다 |
| **초기 시드** | 오픈 커뮤니티/사내 채널을 통한 동시 유입. 소수를 오래 모으는 것보다 다수를 짧게 모으는 게 낫다 |

## 6. 사용자 여정 — 현재 설계의 끊긴 지점

```
[가입] → [로그인] → [조건 입력] → [대기] → [매칭 성사] → ??? → [식사]
                                                        ↑
                                             여기서 여정이 끊긴다
```

**현재 매칭 성사 이후에 존재하는 것**: 그룹원 닉네임 목록, 그룹 채팅방(대화 저장 안 됨, 웹 화면 없음).

**존재하지 않는 것**:
- 참석 확정 절차 → 4명이 묶여도 실제로 몇 명이 나올지 아무도 모른다
- 만날 시각 → `mealDate` + `LUNCH`뿐이다. **12시인지 1시인지 정해지지 않는다**
- 만날 장소 → 지역만 있고 식당·집합 장소가 없다
- 이탈 경로 → 매칭 후에는 취소 API가 동작하지 않아 빠져나갈 방법이 없다

> 설계 노트도 "그룹 확정 동의 ← 제일 중요"라고 스스로 지적했다. 동의한다. **여기가 MVP의 실제 마지막 관문이고, 매칭 알고리즘 개선보다 우선한다.**

### 개선 여정 (to-be)

```
조건 입력 → 대기(잔여시간·대기인원 노출)
  → 매칭 성사 알림(이메일/푸시)
  → [확정 10분] 전원 확정 → CONFIRMED / 미달 시 남은 인원 유지 or 해체 후 대기열 복귀
  → 채팅방 오픈 + 시각·장소 합의 (제안 → 동의 → 확정 카드 고정)
  → 만남 1시간 전 리마인드
  → 식사
  → 참석 상호 체크 → 노쇼 기록 / 신고·차단
```

## 7. MVP 범위

### MVP에 반드시 포함 (P0)

| 영역 | 항목 | 사유 |
|---|---|---|
| 매칭 | 주기적 편성 스케줄러 | 현재는 신규 신청이 없으면 3명이 대기해도 안 묶인다 |
| 매칭 | 지역 enum화 + 서버 날짜 검증 | 버킷 키가 자유 문자열이면 매칭이 조용히 실패한다 |
| **확정** | 확정 단계, 미확정 처리, 확정 후 이탈 | 노쇼 통제 없이는 지표 자체가 성립 안 됨 |
| **만남** | 만날 시각·장소 합의 기능 | 없으면 "만난다"가 완결되지 않음 |
| 채팅 | 메시지 저장 + 조회 + **웹 채팅 화면** | 현재 콘솔 클라이언트만 존재 |
| 알림 | 매칭 성사·확정 요청 알림 (최소 이메일) | 30분 대기 결과를 폴링으로만 아는 건 결함 |
| **안전** | 신고, 차단, 안전 수칙 고지, 약관 동의 | 낯선 사람 대면 서비스의 출시 최소 조건 |
| 계정 | 이메일 인증, 만 19세 이상 제한 | 안전 기능이 우회되지 않게 하는 전제 |
| 운영 | 매칭 성사율·대기시간 지표 수집 | 다음 결정을 위한 근거 |

### v1.1 (출시 직후)

나이대 조건, 노쇼 이력·페널티, 재신청(조건 재사용), 대기 인원 노출, 만료 임박 시 3인 마감 정책, 관리자 신고 처리 화면, refreshToken 자동 갱신.

### 이후

한 줄 소개·관심사 프로필, 만남 후 상호 평가, 식당 추천, 자유 텍스트 취향 + 임베딩(H2 실패 시), 지역 확장.

### 범위 밖
결제·더치페이, 1:1 매칭, 정기 모임, 네이티브 앱, 위치 실시간 공유.

## 8. 유지할 기획 결정 (설계 노트 승계)

이 결정들은 근거가 타당하므로 그대로 간다. 상세 논거는 `docs/matching-design.md` 참조.

| 결정 | 근거 요약 |
|---|---|
| 조건은 카테고리 선택, 자유 텍스트·임베딩 안 씀 | 매칭 근거를 설명할 수 있고, 콜드 스타트가 없으며, 인프라가 Spring 하나로 끝난다 |
| 조건을 하드(버킷) / 하드-관계형(쌍방검사) / 소프트(점수)로 분리 | 성별 조건은 상대에 따라 결과가 달라져 버킷 키가 될 수 없다 |
| 그리디 편성 (선착순 씨앗 + 취향 최대 겹침) | 대기 서비스에서는 최적성보다 "먼저 온 사람이 먼저"라는 공정성이 중요 |
| 대기열은 DB 테이블, Redis 안 씀 | 버킷 전체를 읽어 분할하는 건 쿼리의 일 |
| 만료는 저장 상태가 아니라 시각 비교로 계산 | 만료 배치가 필요 없어진다 |
| 동시성은 비관적 락 | `synchronized`는 트랜잭션 커밋 전에 풀려 실제로 막지 못한다 |
| 채팅방 ID = groupId | 방을 따로 만들 필요가 없고 구성원 = 참여자가 자동 성립 |

**단, `MatchRequest.groupId` 컬럼만으로 그룹을 표현하는 결정은 승격 시점이 왔다.**
설계 노트가 정한 승격 조건("그룹 자체에 속성이 생길 때")이 확정 상태·만날 시각·장소 도입으로 충족된다.

## 9. 결정이 필요한 사항

| # | 질문 | 선택지 | 권고 |
|---|---|---|---|
| Q1 | 확정 미달 시 (4인 중 3인 확정) | 3인으로 진행 / 재편성 / 해체 | **3인으로 진행.** 최소 인원을 이미 3인으로 잡았으므로 일관됨 |
| Q2 | 만날 시각을 누가 정하나 | 신청 시 사용자가 입력 / 그룹장이 제안 / 채팅 합의 | **신청 시 30분 슬롯 선택**(12:00/12:30/18:30…). 버킷 키에 넣으면 조율 비용이 0이 된다. 단 버킷이 더 쪼개지므로 유동성과 트레이드오프 |
| Q3 | 장소 결정 | 사용자 자율 / 서비스가 후보 제시 | MVP는 자율. 다만 "집합 장소"만이라도 구조화해서 저장 |
| Q4 | 노쇼 판정 근거 | 상호 체크 / 신고만 / 위치 인증 | **상호 체크.** 위치 인증은 과하다 |
| Q5 | 오픈 지역 | 7곳 전체 / 1~2곳 | **1~2곳.** 5번(유동성) 참조 |
| Q6 | 프로필 공개 범위 | 닉네임만 / +나이대 / +한줄소개 | **닉네임 + 나이대.** 나이 원본은 비공개, 대역만 |
| Q7 | `yumm-inference` | 유지 / 삭제 | **삭제.** 호출하는 코드가 없고 카테고리 매칭 결정과 상충. H2 실패 시 다시 만든다 |

## 10. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 유동성 부족으로 매칭 미성사 | **치명적** | 지역·날짜 축소, 시간 집중, 대기 인원 노출 (5번) |

## 11. 마일스톤

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| M0 (완료) | 인증/회원, 매칭 편성 로직, 그룹 채팅 서버, 매칭 웹 화면 | 현재 상태 |
| M1 | 편성 스케줄러, 지역 enum, 서버 날짜 검증, 지표 수집 | 신규 신청 없이도 대기자가 묶인다 |
| M2 | **확정 단계 + 만남 시각·장소 + 그룹 엔티티 승격** | 매칭 이후 여정이 끝까지 이어진다 |
| M3 | 채팅 저장·조회 + 웹 채팅 화면 + 매칭 알림 | 앱을 켜두지 않아도 매칭을 알 수 있다 |
| M4 | 신고·차단·약관·안전 수칙·성인 인증 | **출시 가능 상태** |
| M5 | 1개 지역 클로즈드 베타 | 매칭→만남 전환율 측정 |
| M6 | 노쇼 페널티, 나이대 조건, 관리자 화면, 지역 확장 | |

**M4 이전에는 외부 공개 출시하지 않는다.**
