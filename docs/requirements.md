## 1. 용어 정의

| 용어 | 정의 |
|---|---|
| 밥메이트 | 함께 밥을 먹기 위해 매칭된 상대 |
| 매칭 신청 | 사용자가 조건(지역·날짜·시간대·성별조건·선호음식)을 입력하고 대기열에 들어가는 행위 |
| 버킷 | 지역 + 날짜 + 시간대가 완전히 일치하는 대기자 묶음. 같은 버킷 안에서만 그룹이 만들어진다 |
| 그룹 | 매칭 성사된 2~4인 단위. 시스템 상 동일 `groupId`를 가진 신청들의 집합 |
| 하드 조건 | 어긋나면 매칭 자체가 불가능한 조건 (지역, 날짜, 시간대, 성별 조건) |
| 소프트 조건 | 어긋나도 매칭은 되지만 점수에 반영되는 조건 (선호 음식) |
| 2인 허용 | 신청자가 "2명이어도 좋다"고 선택하는 옵션. 기본값은 미선택(3~4인만) |
| 2인 폴백 | 3인을 채우지 못한 대기자 중 **양쪽 모두 2인 허용**인 사람끼리, 만료 임박 시에만 2인으로 성사시키는 규칙 |
| 노쇼 | 확정한 뒤 실제로 나타나지 않는 행위 |

## 3. 기능 요구사항

### 3.1 계정 · 인증

> **가입 문턱 원칙**: 게이트를 없애지 않고 **뒤로 미룬다.** 가입 시점에는 최소 항목만 받고,
> 인증·동의·고지는 **첫 매칭 신청 직전 한 화면**에서 한 번에 처리한다. 게이트 개수는 같지만
> 체감 문턱은 절반 이하가 되고, 신청할 마음이 생긴 뒤에 요구하므로 이탈률이 낮다.

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-A-01 | **이메일·비밀번호·닉네임·성별·생년**만으로 회원가입한다 | P0 | 🟡 | **[수정 필요]** 현재 `SignupRequest`가 전화번호를 필수로 받는다 → 제거 |
| FR-A-01a | 전화번호는 가입 시 받지 않는다 | P0 | ❌ | **[수정 필요]** 저장·수정만 되고 어디에도 쓰이지 않는다. 문자 발송도, 화면 노출도, 매칭 사용도 없다. `findByPhoneNumber`는 호출부가 없다. 아무 데도 안 쓰는 값이 가장 큰 이탈 지점이 되고 있다 |
| FR-A-01b | 나이는 `age`(정수)가 아니라 **생년**으로 저장한다 | P0 | ❌ | **[수정 필요]** `age`는 시간이 지나면 틀어진다. 성인 판정의 근거로 쓰려면 생년이어야 한다 |
| FR-A-02 | 이메일 중복 가입을 차단한다 | P0 | ✅ | `DUPLICATE_EMAIL` |
| FR-A-03 | 이메일 인증을 통과해야 매칭 신청이 가능하다. **가입 시점이 아니라 첫 신청 직전에 요구한다** | P0 | ❌ | **신규.** 인증 없으면 차단 회원의 재가입을 막을 수 없다. 다만 가입을 막을 이유는 없으므로 게이트를 신청 직전으로 미룬다 |
| FR-A-04 | 만 19세 미만은 서비스를 이용할 수 없다. 확인은 **생년 입력만**으로 하고 별도 본인인증(PASS 등)은 두지 않는다 | P0 | ❌ | **신규.** 근거는 아래 박스 참조. 본인인증은 사고가 관측되기 전엔 과하다 |
| FR-A-05 | 로그인 시 accessToken/refreshToken을 발급한다 | P0 | ✅ | `POST /api/auth/login` |
| FR-A-06 | accessToken 만료 시 refreshToken으로 자동 재발급한다 | P1 | 🟡 | 서버 `POST /api/auth/refresh`는 있으나 웹이 사용하지 않음(만료 시 재로그인) |
| FR-A-07 | 로그아웃 시 refreshToken을 무효화한다 | P0 | ✅ | Redis 블랙리스트 |
| FR-A-08 | 회원 탈퇴 시 개인정보를 삭제한다. 단 신고 이력은 정책 기간 보존한다 | P1 | 🟡 | 탈퇴 API는 있으나 진행 중인 매칭·그룹 처리 정책 없음 |
| FR-A-09 | 비밀번호는 8자 이상, 영문·숫자 조합이어야 한다 | P1 | 🟡 | 프론트만 `minLength=8`, 서버 검증 없음 |
| FR-A-10 | 로그인·가입 없이 지역별 대기 인원을 둘러볼 수 있다 | P1 | ❌ | 가입 전에 "여기 사람이 있다"를 보여줘야 가입할 이유가 생긴다 |

> **연령 하한을 만 19세로 잡은 근거** — 법적 강제가 아니라 **정책 선택**이다.
> 법이 강제하는 선은 만 14세 미만(개인정보보호법상 법정대리인 동의 필수)이고, 만 14~19세는 우리가 정한다.
>
> 1. 이 서비스의 최종 산출물은 **낯선 사람과의 오프라인 대면**이다. 2인 폴백을 켜면 성인 1명과
>    미성년자 1명이 단둘이 만나는 조합이 **시스템에 의해 자동으로** 만들어진다. 신고·차단은 사후 대응이고,
>    조합 자체를 만들지 않는 것이 유일하게 확실한 방법이다.
> 2. 미성년자가 얽힌 사고는 대응 난이도·법적 책임·평판 리스크가 다른 차원이다. 초기 소규모 팀이 감당할 수 없다.
> 3. 타깃(업무·대학 상권 20~30대)과 겹치지 않아 **얻는 유입이 사실상 0**이다.
> 4. 안전하게 받으려면 성인/미성년 버킷을 분리해야 하는데, **최대 리스크가 이미 유동성 부족**이라
>    여기서 버킷을 또 가르면 양쪽 다 매칭이 안 된다. "받되 분리"가 가장 나쁜 선택이다.
>
> 지금 닫아두고 나중에 여는 비용은 낮지만, 열어두고 사고 난 뒤 닫는 비용은 회복 불가다.
> 대안(만 14세 이상 + 법정대리인 동의 + 연령 분리)은 `product-plan.md` 9절 Q8 참조.

### 3.4 그룹 편성

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-G-01 | 같은 버킷(지역+날짜+시간대) 안에서만 그룹을 만든다 | P0 | ✅ | |
| FR-G-02 | 그룹은 최대 4인이며, 최소 인원은 구성원 전원이 수용하는 값이다. 전원이 2인 허용이면 2인, 아니면 3인 | P0 | 🟡 | 현재 `MIN_SIZE`가 3 고정. 후보별 최소 인원으로 바꾸고 성사 판정을 `그룹 크기 >= 구성원 최소인원의 최댓값`으로 변경 |
| FR-G-03 | 성별 조건은 쌍방이 서로를 수용해야 하며, 신규 합류자는 기존 구성원 전원과 검사를 통과해야 한다 | P0 | ✅ | `compatible(a,b) = accepts(a,b) && accepts(b,a)` |
| FR-G-04 | 선호 음식이 많이 겹칠수록 우선 합류한다. 동점이면 먼저 신청한 사람이 우선한다 | P0 | ✅ | |
| FR-G-05 | 동시 신청 시 한 사람이 두 그룹에 배정되지 않는다 | P0 | ✅ | 버킷 조회에 `PESSIMISTIC_WRITE` |
| FR-G-06 | 편성은 **스케줄러에서만** 주기적으로 실행한다. 신청 시점 편성은 제거한다 | P0 | ✅ | `MatchScheduler` 30초 주기. `POST /api/match` 응답은 항상 `WAITING` |

> **편성 트리거를 스케줄러로 일원화한다** (NFR-08 동시 해소)
>
> `@Scheduled`를 얹으면 신청 시점 편성은 중복이 된다. 빼면 세 가지가 한 번에 정리된다.
> - 신청 API가 저장만 하므로 **편성 실패가 신청을 롤백시키지 않는다** (NFR-08)
> - 비관적 락 경합이 신청 경로에서 사라진다
> - 코드가 줄어든다
>
> **비용**: 신청 즉시 성사되던 경우가 최대 1주기만큼 지연된다. 주기를 30초~1분으로 잡으면
> 프론트가 이미 10초 폴링 중이라 체감 차이가 없고, 애초에 3~4인이 한순간에 모여 즉시 성사되는
> 경우 자체가 드물다. `POST /api/match` 응답은 항상 `WAITING`이 되며, 성사는 조회·알림이 전달한다.
>
> 즉시 성사 응답을 굳이 유지하고 싶다면 대안은 편성만 별도 트랜잭션(`REQUIRES_NEW`)으로 분리하는
> 것이지만, 스케줄러가 어차피 필요한 이상 트리거를 둘로 두는 값을 하지 못한다.
| FR-G-07 | 만료 임박(잔여 5분 이내) 시에만 3인으로 마감하고, 여유가 있으면 4인을 기다린다 | P2 | ❌ | 설계 노트의 미결 사항. FR-G-06 도입 후 판단 |
| FR-G-08 | 편성은 3~4인을 먼저 시도하고, 남은 대기자에 한해 2인 폴백을 적용한다 | P0 | ❌ | **신규.** 3명을 모을 수 있는데 2명으로 마감하면 손해다 |
| FR-G-09 | 2인 폴백은 만료 잔여 5분 이내인 신청에만 적용한다 | P0 | ❌ | **신규.** 폴백이지 기본값이 아니다 |
| FR-G-10 | 2인 허용은 쌍방이 모두 선택했을 때만 성립한다 | P0 | ❌ | **신규.** 성별 조건과 동일한 하드·관계형 조건. `compatible()`에 조건 하나를 더하는 형태로 구현 |

### 3.5 참석 · 만남

> **전제**: 별도의 "확정 버튼" 단계는 만들지 않는다. 알림 인프라가 없어 확정하라는 사실을 알 방법이
> 없고, 그 상태로 기한을 걸면 **확정을 안 한 사람과 확정할 기회가 없었던 사람이 구분되지 않는다.**
> 참석 의사는 **채팅방 입장으로 대신 표현**한다. (근거: `docs/matching-design.md` 8절)
> 만날 시각·장소도 시스템이 정하지 않고 그룹이 채팅으로 정한다.

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-C-01 | 그룹 편성 즉시 채팅방이 열리고, 입장이 곧 참석 의사로 간주된다 | P0 | ✅ | 웹 채팅 화면까지 붙어 실제로 입장 가능 |
| FR-C-02 | 매칭된 사용자는 그룹에서 이탈할 수 있다 | P0 | ❌ | **[수정 필요]** 현재 `cancel()`은 WAITING만 허용 → 매칭된 사용자는 빠져나갈 방법이 없다 |
| FR-C-03 | 이탈로 인원이 최소 인원 미만이 되면 그룹을 해체하고 남은 구성원을 대기열로 복귀시킨다 | P0 | ❌ | 2인 그룹에서 1명이 나가면 남은 1명이 방치된다 |
| FR-C-04 | 그룹 해체·이탈 사실을 남은 구성원에게 알린다 | P0 | ❌ | 알림 없이 해체하면 사용자는 계속 기다린다 |
| FR-C-05 | 채팅방에 만날 시각·장소를 약속 카드로 고정한다(제안 → 동의) | P1 | ❌ | 대화에만 맡기면 스크롤에 묻힌다. 시각을 **정하는** 게 아니라 **정한 것을 남기는** 기능 |
| FR-C-06 | 만남 종료 후 참석 여부를 상호 체크한다 | P1 | ❌ | 노쇼 집계의 원천 데이터 |

## 8. 제약 및 가정

- 초기 서비스 지역은 수도권 주요 상권 7곳(강남·홍대·신촌·건대·종로·여의도·판교)으로 한정한다.
- 결제·정산 기능은 범위 밖이다. 식대는 사용자끼리 현장에서 처리한다.
- 식당 예약·추천은 범위 밖이다. 장소는 그룹이 채팅으로 정한다.
- 웹(모바일 웹 포함)만 제공한다. 네이티브 앱은 범위 밖이다.
- `yumm-inference`(FastAPI + FAISS 스켈레톤)는 현재 어디에서도 호출되지 않으며, 카테고리 기반 매칭 결정에 따라 **삭제 대상**이다. 자유 텍스트 취향이 필요해지면 다시 만든다.

## 9. 범위 밖 (명시적 제외)

식당 추천/예약, 결제·더치페이, 정기 모임·동호회, 사진 피드, 위치 기반 실시간 추적, 다국어.

> **"1:1 매칭"은 제공하지 않는다.** 2인 그룹은 옵트인 폴백이지 별도 모드가 아니며, UI·문구 어디에도 "1:1"이라는 표현을 쓰지 않는다. 그 단어가 만드는 기대(소개팅)가 실제 사고와 신고를 만든다.
