# yumm 요구사항정의서

| 항목 | 내용 |
|---|---|
| 문서명 | yumm 밥메이트 서비스 요구사항정의서 |
| 버전 | v0.1 (초안) |
| 작성일 | 2026-08-28 |
| 관련 문서 | `docs/product-plan.md` (기획서), `docs/matching-design.md` (매칭 설계 노트) |

**상태 표기**: ✅ 구현 완료 / 🟡 부분 구현 / ❌ 미구현
**우선순위**: P0 = MVP 출시에 없으면 서비스가 성립하지 않음 / P1 = 출시 직후 필요 / P2 = 이후

---

## 1. 용어 정의

| 용어 | 정의 |
|---|---|
| 밥메이트 | 함께 밥을 먹기 위해 매칭된 상대 |
| 매칭 신청 | 사용자가 조건(지역·날짜·시간대·성별조건·선호음식)을 입력하고 대기열에 들어가는 행위 |
| 버킷 | 지역 + 날짜 + 시간대가 완전히 일치하는 대기자 묶음. 같은 버킷 안에서만 그룹이 만들어진다 |
| 그룹 | 매칭 성사된 3~4인 단위. 시스템 상 동일 `groupId`를 가진 신청들의 집합 |
| 하드 조건 | 어긋나면 매칭 자체가 불가능한 조건 (지역, 날짜, 시간대, 성별 조건) |
| 소프트 조건 | 어긋나도 매칭은 되지만 점수에 반영되는 조건 (선호 음식) |
| 확정 | 그룹 편성 후 각 구성원이 실제 참석 의사를 밝히는 단계 |
| 노쇼 | 확정한 뒤 실제로 나타나지 않는 행위 |

---

## 2. 사용자 및 역할

| 역할 | 설명 | 권한 |
|---|---|---|
| 비회원 | 미가입/미로그인 | 랜딩, 회원가입, 로그인 |
| 회원 (ROLE_USER) | 가입·로그인 완료 | 프로필 관리, 매칭 신청/취소, 그룹 채팅, 신고 |
| 관리자 (ROLE_ADMIN) | 운영자 | 신고 처리, 계정 정지, 매칭 지표 조회 |

> **[수정 필요]** `UserRole.ROLE_ADMIN`은 enum에만 존재하고 관리자용 API·화면이 전혀 없다. 신고 기능을 넣는 순간 필수가 된다.

## 3. 기능 요구사항

### 3.1 계정 · 인증

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-A-01 | 이메일·비밀번호·닉네임·성별·나이·전화번호로 회원가입한다 | P0 | ✅ | `POST /api/user/signup` |
| FR-A-02 | 이메일 중복 가입을 차단한다 | P0 | ✅ | `DUPLICATE_EMAIL` |
| FR-A-03 | 이메일 인증(인증코드/링크)을 통과해야 매칭 신청이 가능하다 | P0 | ❌ | **신규.** 인증 없으면 노쇼·차단 회원의 재가입을 막을 수 없다 |
| FR-A-04 | 만 19세 미만은 가입할 수 없다 | P0 | ❌ | **신규.** 현재 `age`는 1~120 허용. 낯선 성인과 오프라인 대면 서비스라 미성년자 차단 필수 |
| FR-A-05 | 로그인 시 accessToken/refreshToken을 발급한다 | P0 | ✅ | `POST /api/auth/login` |
| FR-A-06 | accessToken 만료 시 refreshToken으로 자동 재발급한다 | P1 | 🟡 | 서버 `POST /api/auth/refresh`는 있으나 웹이 사용하지 않음(만료 시 재로그인) |
| FR-A-07 | 로그아웃 시 refreshToken을 무효화한다 | P0 | ✅ | Redis 블랙리스트 |
| FR-A-08 | 회원 탈퇴 시 개인정보를 삭제한다. 단 신고 이력은 정책 기간 보존한다 | P1 | 🟡 | 탈퇴 API는 있으나 진행 중인 매칭·그룹 처리 정책 없음 |
| FR-A-09 | 비밀번호는 8자 이상, 영문·숫자 조합이어야 한다 | P1 | 🟡 | 프론트만 `minLength=8`, 서버 검증 없음 |

### 3.3 매칭 신청

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-M-01 | 지역·날짜·시간대·성별조건·선호음식(1개 이상)을 입력해 신청한다 | P0 | ✅ | `POST /api/match` |
| FR-M-02 | 지역은 서비스가 정한 고정 목록에서만 선택할 수 있다 | P0 | 🟡 | **[수정 필요]** 프론트는 7개 고정인데 서버는 `@NotBlank String`. 서버에서 API를 직접 호출하면 "강남구"가 별도 버킷을 만든다 → `Region` enum으로 승격 |
| FR-M-03 | 과거 날짜로는 신청할 수 없다 | P0 | 🟡 | **[수정 필요]** 프론트만 `min=today`, 서버 검증 없음 |
| FR-M-04 | 오늘부터 최대 7일 이내로만 신청할 수 있다 | P1 | ❌ | 무한정 먼 날짜 신청은 대기열만 오염시킴 |
| FR-M-05 | 진행 중인 신청이 있으면 새 신청을 거부한다 | P0 | ✅ | `ALREADY_WAITING` |
| FR-M-06 | 신청은 30분 후 자동 만료되고 상태가 TIMEOUT으로 조회된다 | P0 | ✅ | 조회 시각 비교로 계산, 별도 배치 없음 |
| FR-M-07 | 대기 중인 신청을 취소할 수 있다 | P0 | ✅ | `DELETE /api/match` |
| FR-M-08 | 내 매칭 상태와 그룹 구성원을 조회할 수 있다 | P0 | ✅ | `GET /api/match` |
| FR-M-09 | 만료·취소된 신청에서 같은 조건으로 재신청한다 | P1 | ❌ | 지금은 폼을 처음부터 다시 채워야 함 |
| FR-M-10 | 대기 화면에 현재 같은 버킷의 대기 인원을 보여준다 | P1 | ❌ | 30분을 아무 정보 없이 기다리게 하면 이탈한다 |
| FR-M-11 | 상대 나이대 조건(±5세 / 20대 / 30대 / 상관없음)을 선택한다 | P1 | ❌ | **신규.** 성별만으로는 불만이 해소되지 않음. 성별 조건과 동일한 쌍방 검사 구조 재사용 |

### 3.4 그룹 편성

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-G-01 | 같은 버킷(지역+날짜+시간대) 안에서만 그룹을 만든다 | P0 | ✅ | |
| FR-G-02 | 그룹은 최소 3인, 최대 4인이다 | P0 | ✅ | `GroupMatcher.MIN_SIZE/MAX_SIZE` |
| FR-G-03 | 성별 조건은 쌍방이 서로를 수용해야 하며, 신규 합류자는 기존 구성원 전원과 검사를 통과해야 한다 | P0 | ✅ | `compatible(a,b) = accepts(a,b) && accepts(b,a)` |
| FR-G-04 | 선호 음식이 많이 겹칠수록 우선 합류한다. 동점이면 먼저 신청한 사람이 우선한다 | P0 | ✅ | |
| FR-G-05 | 동시 신청 시 한 사람이 두 그룹에 배정되지 않는다 | P0 | ✅ | 버킷 조회에 `PESSIMISTIC_WRITE` |
| FR-G-06 | 신청이 없어도 주기적으로 편성을 시도한다 | P0 | ❌ | **[수정 필요]** 현재 편성 트리거가 신청 시점뿐. 3명이 대기 중이어도 4번째 신청이 없으면 영원히 안 묶인다. `@Scheduled` 1분 주기로 해결 |
| FR-G-07 | 만료 임박(잔여 5분 이내) 시에만 3인으로 마감하고, 여유가 있으면 4인을 기다린다 | P2 | ❌ | 설계 노트의 미결 사항. FR-G-06 도입 후 판단 |

### 3.5 확정 · 만남 ← **가장 큰 공백**

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-C-01 | 그룹 편성 후 각 구성원은 제한시간(10분) 내에 참석을 확정한다 | P0 | ❌ | 확정 개념 자체가 없음 |
| FR-C-02 | 전원 확정 시 그룹이 CONFIRMED가 되고 채팅방이 열린다 | P0 | ❌ | 현재는 편성 즉시 채팅방이 열림 |
| FR-C-03 | 제한시간 내 미확정자가 있으면 해당 인원을 제외한다. 남은 인원이 3인 이상이면 유지, 미만이면 그룹을 해체하고 전원 대기열로 복귀시킨다 | P0 | ❌ | 4인 중 1명이 이탈하면 지금은 그냥 깨진 그룹으로 남음 |
| FR-C-04 | 확정 후에도 취소할 수 있으며, 이때 노쇼 이력에 기록된다 | P0 | ❌ | **[수정 필요]** 현재 `cancel()`은 WAITING만 허용 → 매칭된 사용자는 빠져나갈 방법이 없다 |
| FR-C-05 | 만날 시각(예: 12:30)과 장소를 그룹에서 정할 수 있다 | P0 | ❌ | **[수정 필요]** 지금은 `mealDate` + LUNCH/DINNER뿐이라 "몇 시에 어디서"가 결정되지 않는다. 서비스가 실제로 성립하려면 필수 |
| FR-C-06 | 만남 시각을 제안하고 구성원이 동의하는 방식으로 확정한다 | P1 | ❌ | 채팅 대화에만 맡기면 결정이 안 남는다 |
| FR-C-07 | 만남 종료 후 참석 여부를 상호 체크한다 | P1 | ❌ | 노쇼 집계의 원천 데이터 |

## 4. 비기능 요구사항

| ID | 구분 | 요구사항 | 상태 |
|---|---|---|---|
| NFR-01 | 성능 | 매칭 신청 API 응답 p95 < 500ms | 미측정 |
| NFR-02 | 성능 | 한 버킷 대기자 100명 기준 편성 1초 이내. 그리디 O(n²)이므로 그 이상은 재설계 | 미측정 |

| NFR-05 | 보안 | 비밀번호는 해시 저장, 로그에 토큰·비밀번호를 남기지 않을 것 | 🟡 로깅 정책 미정의 |

| NFR-08 | 가용성 | 매칭 편성 실패가 신청 API 전체를 실패시키지 않을 것 | ❌ 현재 같은 트랜잭션 |
| NFR-09 | 법규 | 개인정보처리방침·이용약관 게시, 탈퇴 시 파기 절차 | ❌ |

## 5. 데이터 요구사항

**현재 존재하는 테이블**

| 테이블 | 용도 |
|---|---|
| `users` | 회원 |
| `match_requests` | 매칭 신청 = 대기열 1자리. `groupId` 컬럼으로 그룹을 표현 |
| `match_request_foods` | 신청별 선호 음식 (다중값) |

**추가로 필요한 것**

| 테이블 | 사유 | 우선 |
|---|---|---|
| `match_groups` | 확정 상태·만날 시각·장소가 생기면 `groupId` 컬럼만으로는 표현 불가 → 엔티티 승격 시점 | P0 |
| `group_confirmations` | 구성원별 확정/거절/무응답. 또는 `match_requests`에 확정 컬럼 추가 | P0 |
| `chat_messages` | 대화 기록 조회(FR-T-03), 신고 증빙 | P0 |
| `reports` | 신고 접수/처리 | P0 |
| `user_blocks` | 차단 관계 (편성에서 쌍방 배제) | P0 |
| `no_show_records` | 노쇼 누적 | P1 |

> **[수정 필요]** `MatchStatus`에 `CONFIRMED`, `BROKEN`(그룹 해체) 상태 추가 필요. `EXPIRED`를 두지 않은 결정(시각 비교로 계산)은 유지해도 좋다.

## 7. 비즈니스 규칙

| ID | 규칙 |
|---|---|
| BR-01 | 사용자당 동시에 유효한 매칭 신청은 1건이다 |
| BR-02 | 그룹 인원은 3~4인. 2인 이하로는 성사시키지 않는다 |
| BR-03 | 성별 조건은 쌍방 충족해야 한다. 한쪽만 만족하는 조합은 금지 |
| BR-04 | 차단 관계인 두 사용자는 같은 그룹에 편성되지 않는다 (신규) |
| BR-05 | 대기 제한시간은 30분이며 초과 시 자동 만료된다 |
| BR-06 | 확정 제한시간은 편성 후 10분이다 (신규) |
| BR-07 | 노쇼 3회 누적 시 7일간 신청이 제한된다 (신규) |
| BR-08 | 미성년자(만 19세 미만)는 서비스를 이용할 수 없다 (신규) |

## 8. 제약 및 가정

- 초기 서비스 지역은 수도권 주요 상권 7곳(강남·홍대·신촌·건대·종로·여의도·판교)으로 한정한다.
- 결제·정산 기능은 범위 밖이다. 식대는 사용자끼리 현장에서 처리한다.
- 식당 예약·추천은 범위 밖이다. 장소는 그룹이 채팅으로 정한다.
- 웹(모바일 웹 포함)만 제공한다. 네이티브 앱은 범위 밖이다.
- `yumm-inference`(FastAPI + FAISS 스켈레톤)는 현재 어디에서도 호출되지 않으며, 카테고리 기반 매칭 결정에 따라 **삭제 대상**이다. 자유 텍스트 취향이 필요해지면 다시 만든다.
