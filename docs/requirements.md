## 1. 용어 정의

| 용어 | 정의 |
|---|---|
| 밥메이트 | 함께 밥을 먹기 위해 매칭된 상대 |
| 매칭 신청 | 사용자가 조건(지역·날짜·시간대·성별조건·선호음식)을 입력하고 대기열에 들어가는 행위 |
| 버킷 | 지역 + 날짜 + 시간대가 완전히 일치하는 대기자 묶음. 같은 버킷 안에서만 그룹이 만들어진다 |
| 그룹 | 매칭 성사된 2~4인 단위. 시스템 상 동일 `groupId`를 가진 신청들의 집합 |
| 하드 조건 | 어긋나면 매칭 자체가 불가능한 조건 (지역, 날짜, 시간대, 성별 조건) |
| 소프트 조건 | 어긋나도 매칭은 되지만 점수에 반영되는 조건 (선호 음식) |
| 2인 허용 | 신청자가 "2명이어도 좋다"고 선택하는 옵션. 기본값은 미선택(3~4인만) |
| 2인 폴백 | 3인을 채우지 못한 대기자 중 **양쪽 모두 2인 허용**인 사람끼리, 만료 임박 시에만 2인으로 성사시키는 규칙 |
| 노쇼 | 확정한 뒤 실제로 나타나지 않는 행위 |

## 2. 사용자 및 역할

| 역할 | 설명 | 권한 |
|---|---|---|
| 비회원 | 미가입/미로그인 | 랜딩, 회원가입, 로그인 |
| 회원 (ROLE_USER) | 가입·로그인 완료 | 프로필 관리, 매칭 신청/취소, 그룹 채팅, 신고 |

> **[수정 필요]** `UserRole.ROLE_ADMIN`은 enum에만 존재하고 관리자용 API·화면이 전혀 없다. 신고 기능을 넣는 순간 필수가 된다.

## 3. 기능 요구사항

### 3.1 계정 · 인증

> **가입 문턱 원칙**: 게이트를 없애지 않고 **뒤로 미룬다.** 가입 시점에는 최소 항목만 받고,
> 인증·동의·고지는 **첫 매칭 신청 직전 한 화면**에서 한 번에 처리한다. 게이트 개수는 같지만
> 체감 문턱은 절반 이하가 되고, 신청할 마음이 생긴 뒤에 요구하므로 이탈률이 낮다.

| ID | 요구사항 | 우선 | 상태 | 비고 |
|---|---|---|---|---|
| FR-A-01 | **이메일·비밀번호·닉네임·성별·생년**만으로 회원가입한다 | P0 | ✅ | `SignupRequest`가 이 5개만 받는다. 컨트롤러의 `@Valid`는 DTO에 제약이 있어야만 동작한다 — 이전에는 `birthYear`·`agreedToTerms`에만 제약이 있어 나머지 4개가 무검증이었고(누락 시 NPE·BCrypt 예외·NOT NULL 위반이 500으로 샜다) 지금은 `email`(@NotBlank/@Email/@Size), `password`(@NotBlank/@Pattern), `nickname`(@NotBlank/@Size), `gender`(@NotBlank)까지 걸어 전부 400이다. enum 밖 성별값은 `INVALID_GENDER`(400, 이전 404) |
| FR-A-01a | 전화번호는 가입 시 받지 않는다 | P0 | ✅ | 엔티티·DTO·수정 API·리포지토리 메서드까지 전부 제거. `PUT /api/user/phone-number`는 폐기했다(해당 DTO에 게터가 없어 애초에 동작하지 않던 엔드포인트였다) |
| FR-A-01b | 나이는 `age`(정수)가 아니라 **생년**으로 저장한다 | P0 | ✅ | `birth_year`(int, 출생연도). 생년월일이 아닌 이유는 5절 참조 |
| FR-A-02 | 이메일 중복 가입을 차단한다 | P0 | ✅ | `DUPLICATE_EMAIL` |
| FR-A-03 | 이메일 인증을 통과해야 매칭 신청이 가능하다. **가입 시점이 아니라 첫 신청 직전에 요구한다** | P0 | ✅ | `POST /api/user/verify-email`(발송) · `/confirm`(확인). 코드는 6자리 숫자를 Redis에 `emailVerify:{userId}`로 10분 TTL로 두고, 재발송은 같은 키를 덮어 이전 코드를 무효화한다. 완료 표시는 `users.email_verified_at`. 막는 건 `POST /api/match` 하나뿐이라 가입·로그인·프로필 수정은 미인증으로도 된다 — 실패는 `EMAIL_NOT_VERIFIED`(403). 이메일을 바꾸면 인증이 풀린다 |
| FR-A-04 | 만 19세 미만은 서비스를 이용할 수 없다. 확인은 **생년 입력만**으로 하고 별도 본인인증(PASS 등)은 두지 않는다 | P0 | ✅ | 가입 시 `올해 - 생년 >= 20`만 통과시킨다. 생일 미경과를 가정한 보수적 판정이라 경계 대상은 최대 1년 늦게 가입한다. `UNDERAGE_NOT_ALLOWED`(403) |
| FR-A-05 | 로그인 시 accessToken/refreshToken을 발급한다 | P0 | ✅ | `POST /api/auth/login` |
| FR-A-06 | accessToken 만료 시 refreshToken으로 자동 재발급한다 | P1 | 🟡 | 서버 `POST /api/auth/refresh`는 있으나 웹이 사용하지 않음(만료 시 재로그인) |
| FR-A-07 | 로그아웃 시 refreshToken을 무효화한다 | P0 | ✅ | Redis 블랙리스트 |
| FR-A-08 | 회원 탈퇴 시 개인정보를 삭제한다. 단 신고 이력은 정책 기간 보존한다 | P1 | ✅ | **하드 삭제가 아니라 익명화다.** `users` 행은 남기고 이메일·비밀번호·닉네임·프로필이미지를 지운 뒤 `withdrawn_at`을 찍는다. 신고·차단·채팅·매칭 신청이 이 행을 NOT NULL FK로 물고 있어 삭제하면 FK 위반으로 실패하고, 성공하더라도 보존하기로 한 신고 이력이 함께 사라진다(`docs/privacy-policy.md` 5절). 이메일은 유니크 제약이 있어 `withdrawn-{id}@yumm.invalid`로 덮는다 — 원래 주소는 비므로 재가입할 수 있다. 진행 중인 매칭은 MATCHED면 그룹 이탈(FR-C-02), WAITING이면 신청 취소로 정리한다. 탈퇴 시 `email_verified_at`도 비운다 — 안 비우면 살아 있는 토큰으로 매칭 신청의 이메일 인증 게이트를 그대로 통과한다. 탈퇴 계정 로그인은 `WITHDRAWN_ACCOUNT`(403)이고, **이미 발급된 Access Token(최대 10시간)은 `JwtAuthenticationFilter`가 요청마다 `withdrawn_at`을 확인해 401 `WITHDRAWN_ACCOUNT`로 끊는다** — 서비스마다 `isWithdrawn()`을 흩어 놓으면 새 엔드포인트에서 빠지므로 모든 인증 요청이 지나는 필터 한 곳에서 거른다. 탈퇴 요청에 실린 토큰은 그 자리에서 블랙리스트에 넣는다(이전에는 `invalidateAllUserTokens(userId, null)`이라 아무것도 안 들어갔다). **성별·생년은 NOT NULL이라 남아 있다**(방침 5절은 삭제 대상으로 적고 있다 — 정합 필요) |
| FR-A-09 | 비밀번호는 8자 이상, 영문·숫자 조합이어야 한다 | P1 | ✅ | 서버에서 `SignupRequest.password`에 `@Pattern`(영문 1자 이상 + 숫자 1자 이상, 8~64자)으로 검증한다. 상한 64는 BCrypt가 72바이트 뒤를 잘라내기 때문이다. 프론트 `minLength=8`은 보조. 비밀번호 **변경**(`ChangePasswordRequest`)에는 아직 같은 제약이 없다 |
| FR-A-10 | 로그인·가입 없이 지역별 대기 인원을 둘러볼 수 있다 | P1 | ❌ | 가입 전에 "여기 사람이 있다"를 보여줘야 가입할 이유가 생긴다 |

> **연령 하한을 만 19세로 잡은 근거** — 법적 강제가 아니라 **정책 선택**이다.
> 법이 강제하는 선은 만 14세 미만(개인정보보호법상 법정대리인 동의 필수)이고, 만 14~19세는 우리가 정한다.
>
> 1. 이 서비스의 최종 산출물은 **낯선 사람과의 오프라인 대면**이다. 2인 폴백을 켜면 성인 1명과
>    미성년자 1명이 단둘이 만나는 조합이 **시스템에 의해 자동으로** 만들어진다. 신고·차단은 사후 대응이고,
>    조합 자체를 만들지 않는 것이 유일하게 확실한 방법이다.
> 2. 미성년자가 얽힌 사고는 대응 난이도·법적 책임·평판 리스크가 다른 차원이다. 초기 소규모 팀이 감당할 수 없다.
> 3. 타깃(업무·대학 상권 20~30대)과 겹치지 않아 **얻는 유입이 사실상 0**이다.
> 4. 안전하게 받으려면 성인/미성년 버킷을 분리해야 하는데, **최대 리스크가 이미 유동성 부족**이라
>    여기서 버킷을 또 가르면 양쪽 다 매칭이 안 된다. "받되 분리"가 가장 나쁜 선택이다.
>
> 지금 닫아두고 나중에 여는 비용은 낮지만, 열어두고 사고 난 뒤 닫는 비용은 회복 불가다.
> 대안(만 14세 이상 + 법정대리인 동의 + 연령 분리)은 `product-plan.md` 9절 Q8 참조.

### 3.4 그룹 편성

| ID | 요구사항 | 우선 | 상태 | 비고 |

> **편성 트리거를 스케줄러로 일원화한다** (NFR-08 동시 해소)
>
> `@Scheduled`를 얹으면 신청 시점 편성은 중복이 된다. 빼면 세 가지가 한 번에 정리된다.
> - 신청 API가 저장만 하므로 **편성 실패가 신청을 롤백시키지 않는다** (NFR-08)
> - 비관적 락 경합이 신청 경로에서 사라진다
> - 코드가 줄어든다
>
> **비용**: 신청 즉시 성사되던 경우가 최대 1주기만큼 지연된다. 주기를 30초~1분으로 잡으면
> 프론트가 이미 10초 폴링 중이라 체감 차이가 없고, 애초에 3~4인이 한순간에 모여 즉시 성사되는
> 경우 자체가 드물다. `POST /api/match` 응답은 항상 `WAITING`이 되며, 성사는 조회·알림이 전달한다.
>
> 즉시 성사 응답을 굳이 유지하고 싶다면 대안은 편성만 별도 트랜잭션(`REQUIRES_NEW`)으로 분리하는
> 것이지만, 스케줄러가 어차피 필요한 이상 트리거를 둘로 두는 값을 하지 못한다.

### 3.5 참석 · 만남

> **전제**: 별도의 "확정 버튼" 단계는 만들지 않는다. 알림 인프라가 없어 확정하라는 사실을 알 방법이

## 9. 범위 밖 (명시적 제외)

식당 추천/예약, 결제·더치페이, 정기 모임·동호회, 사진 피드, 위치 기반 실시간 추적, 다국어.
