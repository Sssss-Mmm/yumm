# yumm 밥메이트 매칭 설계 노트

작성일: 2026-08-28

3~4인 밥메이트 매칭을 어떻게 만들지 정리한 문서. 결정된 것과 아직 안 정한 것을 나눠 적는다.
"왜 그렇게 안 했는지"를 남기는 게 목적이라, 검토했다 버린 안도 함께 적는다.

---

## 0. 배경

- **하려던 것**: 혼자 밥 먹기 싫은 사람들을 묶어주는 서비스.
- **핵심 제약**: 1:1이 아니라 **3~4명 그룹**. 이게 설계 전체를 좌우한다.
- **기존 코드 상태**: 인증/회원 도메인만 완성. 매칭은 들어내진 상태였고
  `ErrorCode.MATCHING_TIMEOUT`, `CHAT_ROOM_NOT_FOUND`, `MESSAGE_SEND_FAILED`와
  `console-client/stateMachine.js`의 주석 처리된 `MATCHING` 이벤트가 흔적으로 남아 있었다.
  → 원래 **대기열 + 타임아웃 + 매칭 후 채팅** 구조를 염두에 뒀던 것으로 보이고, 이 문서는 그 방향을 이어간다.

---

## 1. 조건 입력 방식 — 카테고리 선택 vs 자유 텍스트

**결론: 카테고리 선택(체크박스).**

| | 카테고리 | 자유 텍스트 + 임베딩 |
|---|---|---|
| 매칭 근거 설명 | "한식·일식이 겹쳐서" — 바로 보여줌 | 유사도 0.87 — 설명 불가 |
| 신규 사용자 | 즉시 매칭 가능 | 콜드 스타트 |
| 필요 인프라 | Spring 하나 | + 임베딩 모델 + 벡터 저장소 |

밥메이트 조건은 대부분 원래 카테고리형(한식/양식, 점심/저녁, 지역)이라
벡터로 바꿀 만한 연속적 의미가 별로 없다.

**자유 텍스트가 값을 하는 시점**: "조용한 데서 먹고 싶다", "매운 거 못 먹음" 같은
카테고리로 안 잡히는 취향이 매칭 품질에 실제로 영향을 준다고 확인됐을 때. 그때 도입한다.

---

## 2. 조건을 세 종류로 나눈다

이게 설계의 핵심이다. 모든 조건을 똑같이 다루면 안 된다.

| 종류 | 항목 | 처리 방식 |
|---|---|---|
| **하드 · 절대일치** | 지역, 날짜, 점심/저녁 | 대기열 **버킷 키**. 같은 버킷 안은 전원 성사 가능 |
| **하드 · 관계형** | 원하는 성별 | 버킷 키가 될 수 없음 → **합류 시점에 쌍방 검사** |
| **소프트** | 선호 음식 | 겹치는 개수 = **점수**. 안 겹쳐도 매칭은 됨 |

### 성별 조건이 까다로운 이유

지역은 "강남 = 강남"으로 끝나지만, 성별 조건은 **상대에 따라 달라진다**.

```
A(동성만, 남) + B(상관없음, 여)
  → B는 A를 받아들이지만, A가 B를 거절한다
  → 한쪽만 만족하는 매칭은 성사시키면 안 된다
```

그래서 `compatible(a, b) = accepts(a,b) && accepts(b,a)` 로 **쌍방 검사**한다.
그룹에 새로 합류할 때는 **기존 구성원 전원**과 쌍방 검사를 통과해야 한다.

## 3. 그룹 편성 알고리즘

`GroupMatcher.formGroups()` — Spring/JPA에 의존하지 않는 순수 로직으로 분리했다. (테스트가 쉬워진다)

```
1. 대기자를 도착 순으로 정렬
2. 아직 안 묶인 사람 중 가장 오래 기다린 사람을 씨앗으로 잡는다
3. 그룹 전원과 호환되는 후보 중, 음식 취향이 가장 많이 겹치는 사람을 한 명 붙인다
   (동점이면 먼저 온 사람)
4. 4명이 될 때까지 3을 반복
5. 3명 이상이면 성사. 못 채웠으면 그룹을 만들지 않고 씨앗은 대기열에 남긴다
```

**왜 그리디인가**: 전역 최적해가 아니다. 대신 **"먼저 온 사람이 먼저 매칭된다"**를 보장한다.
대기 서비스에서는 공정성이 최적성보다 중요하다고 봤다.
대기자가 수백 명 규모가 되고 매칭 품질이 실제로 문제될 때 지역 탐색을 얹으면 된다.

### 안 정한 것: 3명에 성사 vs 4명까지 대기

지금은 **3명이 모이면 바로 성사**시킨다. 1분만 더 기다리면 4명이 될 수 있어도 3명으로 확정된다.
반대로 4명을 고집하면 3명뿐인 버킷은 영영 성사가 안 된다.

> 타협안: 타임아웃이 임박했을 때만 3명으로 마감하고, 여유가 있으면 4명을 기다린다.
> 노브가 하나 늘어서 일단 안 넣었다.

## 4. 대기열과 타임아웃

**결론: DB 테이블(`match_requests`) + `expires_at` 컬럼. Redis 안 씀.**

Redis는 이미 스택에 있고(`JwtRedisService`가 리프레시 토큰에 사용) TTL이 공짜라 후보였다.
그런데 그룹을 만들려면 **버킷 전체를 읽어서 분할**해야 하는데, 그건 쿼리의 일이다.
Redis로 가면 WHERE 절이 해줄 일을 직접 짜게 된다.

```sql
-- 만료 처리 배치가 필요 없다. 조회할 때 걸러지면 그만이다.
WHERE status = 'WAITING' AND region = ? AND meal_date = ? AND meal_time = ?
  AND expires_at > now()
```

`MatchStatus`에 `EXPIRED`를 두지 않은 이유도 같다. 만료는 **저장된 상태가 아니라 시각 비교로 계산**된다.
상태를 저장하면 그걸 갱신해줄 배치가 필요해진다.

대기 시간은 상수 30분(`MatchServiceImpl.WAIT_MINUTES`). 사용자가 고르게 하고 싶어지면 요청 DTO로 올린다.

## 5. 그룹을 어떻게 표현할까

**결론: `MatchRequest.groupId` 컬럼 하나. `MatchGroup` 엔티티 없음.**

같은 `groupId`를 가진 행들이 곧 한 그룹이다. 엔티티 + 리포지토리 한 쌍을 안 만들어도 된다.

**승격할 시점**: 그룹 자체에 속성이 생길 때 — 식당 이름, 확정 여부, 채팅방 ID 등.
그때는 별도 엔티티가 맞다.

## 6. 동시성 — 같은 사람이 두 그룹에 들어가는 문제

두 명이 동시에 신청하면 각자 같은 대기 풀을 읽어서 **같은 사람을 각자의 그룹에 넣어버릴 수 있다.**

**`synchronized`는 답이 아니다.** `@Transactional` 메서드에 걸면 락이 **커밋 전에** 풀려서
다른 트랜잭션이 커밋 안 된 상태를 읽는다. 막은 것처럼 보이지만 안 막힌다.

**택한 방법**: 버킷 조회에 `@Lock(LockModeType.PESSIMISTIC_WRITE)`.
DB가 행을 잠그므로 트랜잭션 경계와 정확히 일치한다. 애노테이션 한 줄이면 끝난다.

> 트레이드오프: 같은 버킷 신청이 몰리면 직렬화된다. 버킷이 지역·날짜·시간대로 잘게 쪼개져 있어
> 실제 경합은 낮다고 봤다. 문제되면 그때 측정하고 바꾼다.

---

## 7. 편성은 언제 돌리나

**지금: 신청이 들어온 시점에만.** 스케줄러 없음.

**알려진 구멍**: 마지막 신청자는 다음 사람이 올 때까지 그룹이 안 만들어진다.
이미 3명이 대기 중인데 아무도 새로 안 오면 계속 대기 상태다.

**고칠 때**: 대기 시간이 실제로 문제되면 `@Scheduled` 하나 얹으면 된다.
편성 로직 자체는 그대로 재사용된다.

## 8. 아직 안 푼 것

### 그룹 확정 동의 ← 제일 중요

**4명이 매칭됐는데 1명이 안 나오면 그룹이 깨진다.**
실무에서는 유사도 계산보다 이쪽이 훨씬 어렵다. 지금 코드에는 이 단계가 아예 없다.

생각해볼 것:
- 매칭 후 N분 내 전원 확정 안 하면 그룹 해체 → 남은 사람은 대기열 복귀?
- 노쇼 이력 관리가 필요한가?
- 3명 확정 + 1명 미확정이면 3명으로 진행할 것인가?

### 채팅

`ErrorCode`에 `CHAT_ROOM_NOT_FOUND`, `MESSAGE_SEND_FAILED`가 이미 있고,
`console-client/chatClient.js`는 `ws://localhost:8080/ws`로 STOMP 연결을 시도하며
`package.json`에 `@stomp/stompjs`도 들어 있다.

**그런데 서버에는 websocket 스타터도 `@MessageMapping`도 없다.**
클라이언트만 먼저 짜두고 멈춘 상태. 매칭이 굴러가면 그다음 순서.

### 기타

- 프론트(`yumm-web`)는 Vite 템플릿 + Login/Home/Registration 3페이지가 전부. 매칭 화면 없음.
- `지역`이 자유 문자열이라 "강남"과 "강남구"가 다른 버킷이 된다. **선택지로 고정해야 한다.**
- `yumm-inference`는 현재 미사용. 삭제 후보.

## 9. 지금까지 만들어진 것

```
domain/    FoodCategory, MealTime, GenderPreference, MatchStatus, MatchRequest
service/   GroupMatcher (순수 로직), MatchService + impl
repository/ MatchRequestRepository
dto/match/ MatchApplyRequest, MatchStatusResponse, MatchMemberResponse
controller/ MatchController
```

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/match` | 매칭 신청 + 즉시 편성 시도 |
| GET | `/api/match` | 내 매칭 상태 (성사 시 그룹원 포함) |
| DELETE | `/api/match` | 대기 중 신청 취소 |

`SecurityConfig`가 `anyRequest().authenticated()`라 전부 인증 필요. 별도 설정 안 했다.

테스트: `GroupMatcherTest` 6개 (인원 부족 / 4인 성사 / 성별 쌍방 / 동성 3인 / 취향 우선 / 7명 4+3 분할).

```bash
JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./mvnw -Dtest=GroupMatcherTest test
```

> 이 환경은 `java`가 21인데 `javac`가 17이고 `JAVA_HOME`이 비어 있어서
> 그냥 돌리면 `release version 17 not supported`로 실패한다. JAVA_HOME을 지정해야 한다.
