# yumm 밥메이트 매칭 설계 노트

작성일: 2026-08-28

3~4인 밥메이트 매칭을 어떻게 만들지 정리한 문서. 결정된 것과 아직 안 정한 것을 나눠 적는다.
"왜 그렇게 안 했는지"를 남기는 게 목적이라, 검토했다 버린 안도 함께 적는다.

---

## 0. 배경

- **하려던 것**: 혼자 밥 먹기 싫은 사람들을 묶어주는 서비스.
- **핵심 제약**: 1:1이 아니라 **3~4명 그룹**. 이게 설계 전체를 좌우한다.
- **기존 코드 상태**: 인증/회원 도메인만 완성. 매칭은 들어내진 상태였고
  `ErrorCode.MATCHING_TIMEOUT`, `CHAT_ROOM_NOT_FOUND`, `MESSAGE_SEND_FAILED`와
  `console-client/stateMachine.js`의 주석 처리된 `MATCHING` 이벤트가 흔적으로 남아 있었다.
  → 원래 **대기열 + 타임아웃 + 매칭 후 채팅** 구조를 염두에 뒀던 것으로 보이고, 이 문서는 그 방향을 이어간다.

---

## 1. 조건 입력 방식 — 카테고리 선택 vs 자유 텍스트

**결론: 카테고리 선택(체크박스).**

| | 카테고리 | 자유 텍스트 + 임베딩 |
|---|---|---|
| 매칭 근거 설명 | "한식·일식이 겹쳐서" — 바로 보여줌 | 유사도 0.87 — 설명 불가 |
| 신규 사용자 | 즉시 매칭 가능 | 콜드 스타트 |
| 필요 인프라 | Spring 하나 | + 임베딩 모델 + 벡터 저장소 |

밥메이트 조건은 대부분 원래 카테고리형(한식/양식, 점심/저녁, 지역)이라
벡터로 바꿀 만한 연속적 의미가 별로 없다.

**자유 텍스트가 값을 하는 시점**: "조용한 데서 먹고 싶다", "매운 거 못 먹음" 같은
카테고리로 안 잡히는 취향이 매칭 품질에 실제로 영향을 준다고 확인됐을 때. 그때 도입한다.

---

## 2. 조건을 세 종류로 나눈다

이게 설계의 핵심이다. 모든 조건을 똑같이 다루면 안 된다.

| 종류 | 항목 | 처리 방식 |
|---|---|---|
| **하드 · 절대일치** | 지역, 날짜, 점심/저녁 | 대기열 **버킷 키**. 같은 버킷 안은 전원 성사 가능 |
| **하드 · 관계형** | 원하는 성별 | 버킷 키가 될 수 없음 → **합류 시점에 쌍방 검사** |
| **소프트** | 선호 음식 | 겹치는 개수 = **점수**. 안 겹쳐도 매칭은 됨 |

### 성별 조건이 까다로운 이유

지역은 "강남 = 강남"으로 끝나지만, 성별 조건은 **상대에 따라 달라진다**.

```
A(동성만, 남) + B(상관없음, 여)
  → B는 A를 받아들이지만, A가 B를 거절한다
  → 한쪽만 만족하는 매칭은 성사시키면 안 된다
```

그래서 `compatible(a, b) = accepts(a,b) && accepts(b,a)` 로 **쌍방 검사**한다.
그룹에 새로 합류할 때는 **기존 구성원 전원**과 쌍방 검사를 통과해야 한다.

## 3. 그룹 편성 알고리즘

`GroupMatcher.formGroups()` — Spring/JPA에 의존하지 않는 순수 로직으로 분리했다. (테스트가 쉬워진다)

```
1. 대기자를 도착 순으로 정렬
2. 아직 안 묶인 사람 중 가장 오래 기다린 사람을 씨앗으로 잡는다
3. 그룹 전원과 호환되는 후보 중, 음식 취향이 가장 많이 겹치는 사람을 한 명 붙인다
   (동점이면 먼저 온 사람)
4. 4명이 될 때까지 3을 반복
5. 3명 이상이면 성사. 못 채웠으면 그룹을 만들지 않고 씨앗은 대기열에 남긴다
```

**왜 그리디인가**: 전역 최적해가 아니다. 대신 **"먼저 온 사람이 먼저 매칭된다"**를 보장한다.
대기 서비스에서는 공정성이 최적성보다 중요하다고 봤다.
대기자가 수백 명 규모가 되고 매칭 품질이 실제로 문제될 때 지역 탐색을 얹으면 된다.

### 안 정한 것: 3명에 성사 vs 4명까지 대기

지금은 **3명이 모이면 바로 성사**시킨다. 1분만 더 기다리면 4명이 될 수 있어도 3명으로 확정된다.
반대로 4명을 고집하면 3명뿐인 버킷은 영영 성사가 안 된다.

> 타협안: 타임아웃이 임박했을 때만 3명으로 마감하고, 여유가 있으면 4명을 기다린다.
> 노브가 하나 늘어서 일단 안 넣었다.

## 4. 대기열과 타임아웃

**결론: DB 테이블(`match_requests`) + `expires_at` 컬럼. Redis 안 씀.**

Redis는 이미 스택에 있고(`JwtRedisService`가 리프레시 토큰에 사용) TTL이 공짜라 후보였다.
그런데 그룹을 만들려면 **버킷 전체를 읽어서 분할**해야 하는데, 그건 쿼리의 일이다.
Redis로 가면 WHERE 절이 해줄 일을 직접 짜게 된다.

```sql
-- 만료 처리 배치가 필요 없다. 조회할 때 걸러지면 그만이다.
WHERE status = 'WAITING' AND region = ? AND meal_date = ? AND meal_time = ?
  AND expires_at > now()
```

`MatchStatus`에 `EXPIRED`를 두지 않은 이유도 같다. 만료는 **저장된 상태가 아니라 시각 비교로 계산**된다.
상태를 저장하면 그걸 갱신해줄 배치가 필요해진다.

대기 시간은 상수 30분(`MatchServiceImpl.WAIT_MINUTES`). 사용자가 고르게 하고 싶어지면 요청 DTO로 올린다.

## 5. 그룹을 어떻게 표현할까

**결론: `MatchRequest.groupId` 컬럼 하나. `MatchGroup` 엔티티 없음.**

같은 `groupId`를 가진 행들이 곧 한 그룹이다. 엔티티 + 리포지토리 한 쌍을 안 만들어도 된다.

**승격할 시점**: 그룹 자체에 속성이 생길 때 — 식당 이름, 확정 여부, 채팅방 ID 등.
그때는 별도 엔티티가 맞다.

## 6. 동시성 — 같은 사람이 두 그룹에 들어가는 문제

두 명이 동시에 신청하면 각자 같은 대기 풀을 읽어서 **같은 사람을 각자의 그룹에 넣어버릴 수 있다.**

**`synchronized`는 답이 아니다.** `@Transactional` 메서드에 걸면 락이 **커밋 전에** 풀려서
다른 트랜잭션이 커밋 안 된 상태를 읽는다. 막은 것처럼 보이지만 안 막힌다.

**택한 방법**: 버킷 조회에 `@Lock(LockModeType.PESSIMISTIC_WRITE)`.
DB가 행을 잠그므로 트랜잭션 경계와 정확히 일치한다. 애노테이션 한 줄이면 끝난다.

> 트레이드오프: 같은 버킷 신청이 몰리면 직렬화된다. 버킷이 지역·날짜·시간대로 잘게 쪼개져 있어
> 실제 경합은 낮다고 봤다. 문제되면 그때 측정하고 바꾼다.

---

## 7. 편성은 언제 돌리나

**지금: 신청이 들어온 시점에만.** 스케줄러 없음.

**알려진 구멍**: 마지막 신청자는 다음 사람이 올 때까지 그룹이 안 만들어진다.
이미 3명이 대기 중인데 아무도 새로 안 오면 계속 대기 상태다.

**고칠 때**: 대기 시간이 실제로 문제되면 `@Scheduled` 하나 얹으면 된다.
편성 로직 자체는 그대로 재사용된다.

## 8. 아직 안 푼 것

### 그룹 확정 동의 — 만들지 않기로 했다

**4명이 매칭됐는데 1명이 안 나오면 그룹이 깨진다.** 이걸 막으려고
"매칭 후 N분 내 전원 확정" 단계를 검토했지만 만들지 않기로 했다.

**이유: 확정하라는 걸 사용자가 알 방법이 없다.** 푸시도 웹소켓 알림도 없어서
`GET /api/match`를 직접 찔러보는 화면을 켜둔 사람만 확정할 수 있다. 그 상태로 기한을 걸면
**확정을 안 한 사람과 확정할 기회가 없었던 사람이 구분되지 않아** 잘못 없는 사람이 노쇼 처리된다.

식사 시간에서 역산해 기한을 잡는 안도 검토했다 버렸다. `MealTime`은 `LUNCH`/`DINNER`뿐이라
역산할 시각 자체가 없고("점심 = 12시"는 지어낸 값), 미리 신청하면 기한이 몇 시간 뒤가 되어
의미가 없다. **몇 시에 만날지는 시스템이 정하지 않고 그룹이 정한다**는 것이 최종 결론이다.

**대신 채팅으로 흡수한다.** 실제 사람은 확정 버튼을 누르는 게 아니라 채팅방에서
"저 갈게요, 몇 시에 볼까요?" 하고 약속을 잡는다. 채팅방 입장이 곧 참석 의사다.

나중에 알림 인프라가 생기면 다시 판단할 것:
- 3명 확정 + 1명 미확정이면 3명으로 진행 (최소 인원을 만족하고, 제때 확정한 사람을 벌주면 안 됨)
- 노쇼 이력은 남기지 않는다. 시스템 탓인데 사용자를 벌주게 된다

### 채팅 — 저장·조회·웹 화면까지 붙었다

**채팅방 ID는 매칭 그룹의 `groupId`를 그대로 쓴다.** 방을 따로 만들 필요가 없고
그룹 구성원 = 채팅방 참여자가 자동으로 성립한다.

- **메시지를 저장한다.** `chat_messages` + `GET /api/chat/rooms/{groupId}/messages`.
  닉네임과 `type`은 컬럼으로 두지 않았다 — 닉네임은 조인으로 나오고, 저장해두면 개명 시 과거 기록이 어긋난다.
- **구성원 판정은 `existsByGroupIdAndUser_Id` 한 곳이다.** STOMP 구독/발신 차단과 REST 조회 차단이
  같은 쿼리를 쓴다. 판정이 두 벌이면 한쪽만 고쳐지는 날이 온다.
- **웹 채팅 화면**은 네이티브 `WebSocket` 위에 STOMP 프레임을 직접 조립한다(`yumm-web/src/ws.ts`).
  CONNECT/SUBSCRIBE/SEND/MESSAGE 4종뿐이라 40줄 안쪽이고, 클라이언트 라이브러리를 새로 깔지 않았다.
  브라우저는 WS 핸드셰이크 헤더를 못 넣으므로 **JWT는 CONNECT 프레임 헤더로** 보낸다.

남은 것:
- 하트비트·자동 재연결 없음(끊기면 재시도 버튼). 이력 조회와 구독 사이 수백 ms의 메시지는 놓칠 수 있다.
- 내장 심플 브로커라 **서버가 여러 대가 되면 다른 인스턴스의 사람에게 전달되지 않는다.**
- 입장/퇴장 알림 없음, 페이징 없음, 방 종료(FR-T-05) 없음.

### 매칭된 사용자의 재신청 — 날짜로 푼다

MATCHED를 무조건 막으면 `MatchStatus`에 종료 상태가 없어 **한 번 매칭된 사용자가 영원히 재신청할 수 없다.**
종료 상태값이나 만료 배치를 만드는 대신 **식사 날짜가 지났는지**로 판정한다(`MatchRequest.blocksReapply`).
날짜가 당일+익일뿐이라 최대 2일이면 자연히 풀린다.

한계: 오늘 점심에 매칭된 사람은 오늘 저녁을 신청할 수 없다(하루 단위라 시간대를 못 본다).
시간대까지 쪼개면 두 그룹 동시 배정 문제가 돌아오므로 보수적인 쪽을 택했다.
당일 재신청이 필요하면 FR-C-02(그룹 이탈)가 수동 해제를 담당한다.

### 기타

- 프론트(`yumm-web`)에 매칭 화면(`Match.tsx`)이 붙었다. 신청/상태조회/취소가 서버 계약과 일치한다.
  **채팅 화면(`Chat.tsx`)도 붙었다.** `vite.config.ts` 프록시에 `/ws`(`ws: true`)를 추가했다.
  지역은 이제 enum 이름으로 오가고 화면에만 한글 라벨을 쓴다.
- `지역`이 자유 문자열이라 "강남"과 "강남구"가 다른 버킷이 된다. 다만 **enum으로 박는 건 답이 아니다**
  (지역 추가마다 재배포, 데이터를 코드에 박는 꼴). Region 테이블이나 행정동 코드가 맞는데,
  **지역 단위를 구/동/캠퍼스 중 뭘로 할지가 제품 결정이라 그게 정해지기 전엔 뭘 만들어도 추측이다.**
  사람이 몰려서 버킷이 갈리는 게 관측될 때 고쳐도 늦지 않다.
  **프론트는 선택지 7개로 고정했지만 서버는 여전히 아무 문자열이나 받는다.** API를 직접 호출하거나
  `console-client`로 신청하면 버킷이 갈릴 수 있다.
- `yumm-inference`는 삭제했다(2026-08-29). 취향 임베딩이 필요해지면 다시 만든다.

## 9. 지금까지 만들어진 것

```
domain/     FoodCategory, MealTime, GenderPreference, MatchStatus, MatchRequest
service/    GroupMatcher (순수 로직), MatchService + impl
repository/ MatchRequestRepository
dto/match/  MatchApplyRequest, MatchStatusResponse, MatchMemberResponse
dto/chat/   ChatMessageRequest, ChatMessageResponse
config/     WebSocketConfig
security/   StompAuthChannelInterceptor
controller/ MatchController, ChatController
```

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/match` | 매칭 신청 + 즉시 편성 시도 |
| GET | `/api/match` | 내 매칭 상태 (성사 시 그룹원 포함) |
| DELETE | `/api/match` | 대기 중 신청 취소 |

`SecurityConfig`가 `anyRequest().authenticated()`라 전부 인증 필요.
`/ws`만 예외로 열어뒀는데, **HTTP 핸드셰이크에는 Authorization 헤더가 실리지 않기 때문**이다.
실제 인증은 STOMP CONNECT 프레임에서 `StompAuthChannelInterceptor`가 한다.

### 채팅 경로 (클라이언트가 이미 쓰고 있던 규약)

| 구분 | 경로 |
|---|---|
| 연결 | `ws://localhost:8080/ws` (CONNECT 헤더에 `Authorization: Bearer ...`) |
| 구독 | `/sub/chat/room/{groupId}` |
| 발행 | `/pub/chatroom.{groupId}` |

보낸 사람과 방 번호는 **본문이 아니라 인증 정보와 목적지 경로에서** 가져온다. 본문 값은 위조 가능하다.
로그인만으로는 부족해서 SUBSCRIBE/SEND마다 그 그룹의 구성원인지 확인한다.
